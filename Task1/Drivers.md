## 2. Атрибуты качества (с приоритизацией)

| # | Атрибут | Целевое значение | Обоснование |
|---|---------|-----------------|-------------|
| AQ-1 | **P95 ответа новой DSP** | ≤ 80 ms при 18 000 RPS через 3 месяца | Контракт нового DSP; legacy-требование 100 ms не является SLA нового Bidding Service |
| AQ-2 | **Пропускная способность** | 18 000 RPS через 3 месяца; 50 000 RPS через год | Поэтапный рост бизнеса |
| AQ-3 | **Доступность** | SLA 99,9% через год | Годовая бизнес-цель |
| AQ-4 | **Scalability** | Горизонтальное масштабирование без простоев | Поддержка 3.3x роста трафика |

## 3. Технические ограничения

| # | Ограничение | Детали |
|---|-----------|--------|
| TL-1 | **Бюджет ограничен** | Нет возможности для дорогостоящего enterprise-решения |
| TL-2 | **Срок — 3 месяца** для промежуточного решения | Нельзя переписать систему полностью |
| TL-3 | **Непрерывность бизнеса** | Миграция без планового простоя, постепенная эволюция |
| TL-4 | **Команда 35 человек, без SRE** | Решения должны быть простыми в поддержке |
| TL-5 | **Технологический стек зафиксирован** | C++/Go/Python/Node.js — нельзя резко менять |
| TL-6 | **Невозможность полной переписки** | Нужна постепенная миграция (Strangler Fig) |

## 4. Бизнес-ограничения

| # | Ограничение | Детали |
|---|-----------|--------|
| BL-1 | **Дедлайн DSP-интеграции** | Новый партнёр требует подключения в течение 3 месяцев |
| BL-2 | **SLA-штрафы** | Финансовые penalties за деградацию latency и downtime |
| BL-3 | **Репутация** | Потеря клиентов при деградации сервиса |
| BL-4 | **Рост бизнеса** | Двукратный рост пользователей к концу года |

## 5. Приоритизация драйверов

```
Самые критичные:
  1. Через 3 месяца: 18 000 RPS и P95 новой DSP ≤ 80 ms.
  2. Через год: 50 000 RPS и SLA 99,9%.
  3. Финансовая корректность: Finance DB — единственный источник истины денег.
  4. Постепенная миграция без остановки бизнеса.

Наиболее рискованные ограничения:
  - Бюджет (TL-1) + Срок (TL-2) = нельзя делать big bang rewrite
  - Команда без SRE (TL-4) = решения должны быть простыми
```

## 6. Выводы

Архитектурные драйверы однозначно указывают на необходимость:
1. **Изоляции Bidding Service** как первого deployable-сервиса
2. **Асинхронных интеграционных событий** для отделения записи от RTB-пути
3. **Версионированной read model и кэширования** без создания второго источника истины
4. **Горизонтального масштабирования** отдельных компонентов
5. **Эволюционного подхода** (Strangler Fig Pattern) из-за ограничений по бюджету и срокам
