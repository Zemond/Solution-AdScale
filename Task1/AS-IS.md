# AS-IS — Анализ текущей архитектуры AdScale

## 1. Обзор текущей архитектуры

AdScale представляет собой **гибридный монолит**, состоящий из компонентов на четырёх языках (C++, Go, Python, Node.js), развёрнутый на одном production-кластере без контейнеризации.

### Компоненты

| Компонент | Язык | Роль |
|-----------|------|------|
| **Ad Server** | C++, Go | Принимает HTTP-запросы, определяет пользователей, подбирает кандидатов в рекламу |
| **Auction Engine** | C++ | Взвешивание ставок, бизнес-правила, расчёт победителя аукциона |
| **Delivery Service** | Node.js | Формирует HTML/JS-разметку баннера и HTTP response |
| **Statistics Service** | Python | Запись кликов и показов |
| **Financial Service** | Go | Списание средств, выставление счетов, управление балансами |
| **Analytics Service** | Python | Аналитические SQL-запросы по production-БД |
| **Advertiser Dashboard** | Node.js + JS | Web UI для управления кампаниями |

### Внешние системы

- **DSP-партнёры** — отправляют bid requests, получают bid responses по OpenRTB (HTTPS)
- **Пользователи (end users)** — просматривают рекламу, кликают по баннерам
- **Платёжный шлюз** — обработка пополнения рекламных бюджетов
- **PostgreSQL (1 инстанция)** — единая БД для всех данных: кампании, ставки, события, финансы, аналитика

## 2. Выявленные проблемы и риски

### 2.1. Критическое узкое место — Auction Engine

**Проблема:** Синхронные вызовы к PostgreSQL в горячем пути (hot path) аукциона.  
**Влияние:** P95 времени ответа составляет 110–120 ms при действующем требовании legacy-аукциона не более 100 ms.  
**Риск:** рост до 18 000 RPS дополнительно увеличит задержку.
**Severity:** 🔴 Critical

### 2.2. Single Point of Failure — PostgreSQL

**Проблема:** Одна инстанция PostgreSQL без HA, без read-replicas, без failover.  
**Влияние:** Любой сбой базы = полная остановка сервиса.  
**Влияние:** OLTP и аналитические запросы конкурируют за ресурсы одной БД.  
**Риск:** При росте нагрузки пропускная способность БД станет узким горлышком.  
**Severity:** 🔴 Critical

### 2.3. Узкое место записи — Statistics Service

**Проблема:** Синхронная прямая запись событий кликов и показов в PostgreSQL без буферизации и очередей.  
**Влияние:** Высокая write-нагрузка конкурирует с transactional-запросами финансов и аукциона.  
**Риск:** При росте трафика увеличатся конкуренция за ресурсы и вероятность таймаутов.  
**Severity:** 🟠 High

### 2.4. Analytics Service блокирует production-БД

**Проблема:** Тяжёлые аналитические SQL-запросы выполняются напрямую на production-базе.  
**Влияние:** Lock contention, рост latency для всех транзакционных операций.  
**Риск:** Аналитические запросы могут деградировать работу аукциона.  
**Severity:** 🟠 High

### 2.5. Отсутствие кэширования

**Проблема:** Все запросы к данным идут в БД. Нет Redis/Memcached.  
**Влияние:** Дублирующие read-запросы от Ad Server, Advertiser Dashboard, Analytics Service.  
**Риск:** При росте нагрузки БД не справится с read-паттернами.  
**Severity:** 🟠 High

### 2.6. Отсутствие очередей и буферизации

**Проблема:** Нет брокера сообщений для асинхронной обработки событий.  
**Влияние:** В частности, запись статистики синхронна; нет управляемой буферизации и обратного давления.  
**Риск:** При пиковых нагрузках сервисы падают каскадно.  
**Severity:** 🟠 High

### 2.7. Ручной деплой, отсутствие контейнеризации

**Проблема:** Деплой выполняется вручную, нет Docker/Kubernetes.  
**Влияние:** Долгое развёртывание, человеческие ошибки, отсутствие rolling updates.  
**Риск:** Длительные простои при деплое, медленное масштабирование.  
**Severity:** 🟡 Medium

### 2.8. Гибридный стек (4 языка)

**Проблема:** C++/Go/Python/Node.js в одном монолите.  
**Влияние:** Сложность поддержки, сложности с масштабированием отдельных компонентов.  
**Риск:** Невозможность масштабировать критичный Auction Engine отдельно от Analytics Service.  
**Severity:** 🟡 Medium

## 3. Влияние на время отклика

Критический поток проходит через Ad Server, Auction Engine и Delivery Service. Auction Engine синхронно читает PostgreSQL, а Statistics Service синхронно пишет события в ту же базу. Эти операции конкурируют с финансовыми и аналитическими запросами.

## 4. Карта узких мест

| Узкое место | Текущая метрика | Целевая метрика | Gap |
|-------------|----------------|-----------------|-----|
| Legacy-аукцион P95 | 110–120 ms | ≤ 100 ms (текущее требование) | 🔴 |
| Throughput (RTB) | 15 000 RPS | 18 000 RPS (3 мес) / 50 000 RPS (1 год) | 🔴 |
| PostgreSQL HA | Нет | Да | 🔴 |
| P95 ответа новой DSP | ещё не измерен для нового контура | ≤ 80 ms через 3 месяца | 🔴 |
| Uptime | Не измерено | 99.9% | 🟡 |
| Deployment | Ручной | Автоматизированный | 🟠 |

## 5. Риски при игнорировании проблем

1. **Финансовые штрафы** от DSP-партнёра за деградацию latency и простои
2. **Потеря репутации** — рекламодатели уйдут к конкурентам
3. **Каскадные отказы** — один упавший компонент ломает весь поток
4. **Невозможность масштабирования** — не получится подключить других партнёров
5. **Невозможность выполнения бизнес-целей** — рост не обеспечен

## 6. Резюме текущей архитектуры

Текущая архитектура AdScale — **гибридный монолит** с жёсткой связностью компонентов через единую БД. Система работает без запаса производительности и не позволяет независимо масштабировать критичный контур. Ключевые проблемы: синхронные обращения к БД в горячем пути, синхронная запись статистики, отсутствие кэширования и очередей, единая точка отказа БД и отсутствие изоляции потоков. Требуется эволюционная миграция по шаблону Strangler Fig.
